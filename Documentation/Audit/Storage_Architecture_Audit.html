DBreeze / Storage / architectural compatibility review

Архитектурный аудит Storage: текущая версия против эталона

Аудит рассматривает не только diff строк, а реальные runtime-реализации по target-проектам: буферы, кэши, границы flush, rollback/crash recovery, файловую долговечность, backup, remote protocol и удерживаемую память. Главный критерий — валидные legacy-сценарии должны сохранять поведение, формат на диске и не ухудшать устойчиво latency/allocations/working set.

1. Итоговый вердикт

Основной дисковый контракт сохранён, а .NET 8 Storage стал заметно лучше по параллельным чтениям, allocations, bounded recovery и remote large I/O. Однако до полной архитектурной эквивалентности с эталоном остаётся одна подтверждённая потеря legacy-поведения и одно подтверждённое ухудшение steady-state memory.

PASS ≤+0.55%random/cold/mixed P1 gate

Что можно сохранять

  • .NET 8 ReaderWriterLockSlim + positioned RandomAccess.
  • 32 KiB committed-page cache с version invalidation.
  • Streaming rollback/backup parser и 64 KiB copy buffers.
  • 1 MiB remote chunking и server response cap 64 MiB.
  • Overlap-aware rollback coverage и failure-safer table replace.

Что нарушает legacy

  • MEMORY RestoreTableFromTheOtherTable: исторический no-op заменён на NotSupportedException.
  • Тест на MEMORY сейчас закрепляет новое поведение, а не защищает эталонный контракт.

Что требует owner decision

  • Clear(true) → Clear(false) ускоряет append, но удерживает до 1,127,424 байт на таблицу.
  • Raw remote v1 теперь возвращает actual short read и отвергает read >64 MiB.
  • Backup restore больше не вызывает managed Flush() после каждой записи.
Release gate. До исправления Portable backup selector и осознанного решения по MEMORY no-op нельзя утверждать, что все валидные сценарии эталона сохранены. До решения политики seq-buffer нельзя утверждать, что ожидания по удерживаемой памяти не ухудшились.

Сравнивалось

  • Текущие и эталонные исходники Storage, включая target-specific копии.
  • Фактические Compile Include/Remove/Link в каждом .csproj.

Не считалось доказательством

  • Один успешный build без поведенческого сценария.
  • Побайтовое совпадение двух независимо созданных DB: resource-table недетерминирована.
  • Тест, если он закрепляет новое поведение, противоречащее эталону.
  • Снижение Allocated/op как замена измерению retained heap/working set.

Отчёт — point-in-time review рабочего дерева. Существующие незакоммиченные изменения пользователя не изменялись; создан только этот HTML-файл.

5. Критические находки

P0 · confirmed regression

Portable потерял backup-файлы без .ibp

Эталонный Portable выбирал все имена с префиксом dbreeze_ibp_. Текущий Portable BackupRestorer дополнительно требует EndsWith(".ibp"). Общий restorer уже исправлен, но Portable его не компилирует.

Результат: валидный исторический backup молча не восстанавливается на Portable.

P0 · public behavior

MEMORY restore: no-op стал исключением

В обоих эталонных MSR метод RestoreTableFromTheOtherTable ничего не делал. Сейчас common и .NET 8 MSR бросают NotSupportedException. Путь доступен пользователю через Transaction.RestoreTableFromTheOtherFile и public StorageLayer.

Это не binary API break, но observable semantic break для валидного вызова.

P1 · retained memory

Sequential buffer больше не уменьшается после flush

Эталон делал _seqBuf.Clear(true); текущие FSR/RISR делают Clear(false). При точном append 1 MiB fixed-growth buffer достигает 1,127,424 байт и остаётся у каждой открытой hot table.

Это ускоряет append и резко снижает allocations, но ухудшает steady-state working set.

DONE · performance gate

Random64ByteRead gate закрыт

Metadata и 32 KiB buffer разделены. Small reads ≤256 байт допускают page на третьем последовательном обращении к тому же owner/version/page, более крупные — на втором. Cold и mixed workers buffer не удерживают.

Три запуска: random/cold/mixed не хуже эталона более чем на +0.55%; hot reads не хуже pre-change более чем на +2.86%.

6.1 FSR / DISK: новая внутренняя модель

Append ≤1 MiBСсылка/байты попадают в sequential MemoryStorage.
Random updateДо 3,000,000 bytes или 501 distinct offsets.
Rollback originalsТолько ещё не покрытые интервалы, layout type=1.
Durable markerFlush .rol → marker .rhp → hard flush.
Data writesPositioned RandomAccess; cache generation invalidated.
Commit/finalizeHard flush data → marker=0 → committed eof.

Что принципиально сохранено

  • Sequential boundary ровно 1 MiB и direct path только при Length > 1 MiB.
  • Random auto-flush: bytes ≥3,000,000 либо Count > 500.
  • До перезаписи data originals и marker физически сбрасываются.
  • Committed view до TransactionalCommitIsFinished собирается из data + rollback.
  • eofData остаётся logical committed visibility boundary.

Что изменило performance envelope

  • Read concurrency вместо полной сериализации.
  • Positioned I/O вместо общей mutable FileStream.Position.
  • 32 KiB per-thread page cache с lazy buffer; admission на третьем small-read или втором крупном read.
  • FileStream managed buffer фактически отключён (BufferSize=1).
  • Sequential allocation amortized ценой retained capacity.
Не закрытая legacy assumption: random buffer хранит overlapping updates по разным start offsets, но flush сортирует их по offset, а не по времени вызова. Для обратного порядка перекрытий «last call wins» не гарантирован и writer view до commit может отличиться от результата после commit. Комментарий эталона говорит, что такие overlaps «should be not possible», но public StorageLayer это не валидирует.

6.2 MSR / MEMORY

Lock ownership

В .NET 8 MemoryStorage стал internal lock-free helper, а MSR — единственным владельцем RW lock. Это устраняет nested monitors. Common public MemoryStorage сохраняет собственный monitor для старых targets.

Growth model

Data начинается с 16 KiB и растёт шагом 500 KiB; rollback — 16 KiB/128 KiB; helper — 8/10 bytes. Формулы не менялись, но overflow теперь детектируется до wrap-around.

Contract drift

No-op table replacement стал exception. Это нельзя списать на corrupted data, invalid argument или post-dispose: метод вызывается с валидными аргументами через пользовательский Transaction API.

MaxRollbackFileSize = 1 MiB присутствует и в эталоне, и сейчас, но MSR его нигде не читает. Реальная модель — reuse high-watermark rollback MemoryStorage, а не автоматическое shrink/recreate на 1 MiB.

6.3 Backup: encoding сохранён, pipeline заменён

Writer

  • Один reusable header 21 byte под lock.
  • Payload пишется slice-ом без промежуточного full record.
  • Дата interval-file вычисляется arithmetic, без culture-sensitive ToString.
  • Flush, Dispose и смена folder синхронизированы.
  • Legacy record bytes подтверждены round-trip/encoding test.

Restorer

  • Ordinal file order, только historical prefix; extension не часть общего контракта.
  • Record не может пересекать границу backup-файла; truncated file сразу rejected.
  • 64 KiB streaming payload, bounded memory.
  • Handles гарантированно закрываются даже после ошибки/event exception.
  • Restore остаётся non-transactional: уже применённые records не откатываются при corruption.
Общая реализация соответствует historical selector, Portable — нет. Build Portable этого не обнаруживает; нужен отдельный behavioral test через FSFactory с файлами без extension и .custom.

6.4 Remote: lifecycle, chunking и containment

RISR lockОдин storage instance остаётся serialized из-за stateful positions.
1 MiB chunkPosition продвигается на actual bytes.
Protocol v1Wire command/field layout не изменён.
Handler leaseRead-lock удерживает table lifetime на один command.
Per-table lockОдин FileStream Position owner, разные tables параллельны.
Final flushТолько последний write chunk или explicit flush command.

Устранённые архитектурные дефекты

  • Закрытие одного из двух клиентов больше не закрывает shared table второму.
  • Closed table metadata не накапливается бесконечно в handler.
  • Caller buffer offset и EOF-limited read теперь соблюдаются.
  • Malformed packet всегда даёт стабильный {255}.
  • Server не копирует write payload через Substring.

Оставшиеся границы

  • Common containment лексический: junction/symlink внутри root может указывать наружу.
  • Portable handler containment вообще не реализует.
  • Open разных tables сериализован global write lock и выполняет file open под ним.
  • Raw custom client, ожидающий zero padding или read >64 MiB, увидит иное поведение v1.
  • Old-client/current-server и current-client/old-server wire matrix отдельно не зафиксирована.

9. Пользовательский API и disk compatibility

Подтверждено инструментально

  • Binary API surface: current vs baseline для net8 и net472 — совпадает.
  • Builds: netstandard2.1, netcoreapp3.1, net6, net8, net472 и Portable — проходят.
  • Old create → current read/extend и current create → old read/extend — проходят.
  • Cross-version reopen/restore одной цепочки данных — file inventory и SHA-256 совпадают.
  • Backup offset encoding и primary disk files читаются обеими версиями.

Требует отдельного контракта/теста

  • Behavioral MEMORY no-op нельзя увидеть binary API diff-ом.
  • Portable historical backup selector проверяется отдельным FSFactory compatibility test, а не net8 suite.
  • Старый raw remote commander ↔ новый handler в обе стороны не проверен отдельной DLL matrix.
  • Old DLL opening current crash-left segmented rollback не выделен в самостоятельный probe.
  • Независимо созданные DB не обязаны быть byte-identical из-за resource table.

10. Regression evidence и оставшиеся пробелы

Есть проверка

  • DISK/MEMORY: exact 1 MiB и >1 MiB append, writer/committed views.
  • 501 distinct updates, replacement growth, transactional rollback/finish.
  • Page cache: lazy metadata/buffer admission, lifecycle, cross-page, restore/recreate и concurrent commits.
  • Disk crash recovery с overlapping updates; remote fragmented exact reads.
  • Common backup: no extension/custom extension/order/foreign progress/truncation/delete.
  • Portable backup: no extension/custom extension/order/foreign progress и SHA-256 parity.
  • Remote: shared opens, caller offsets, partial reads, 1 MiB chunks, single final flush.
  • Containment: .., absolute, sibling-prefix, invalid UTF-8, valid nested.
  • Missing restore source не уничтожает destination; invalid settings fail before files.

Нет достаточной проверки

  • Retained heap при 100/1,000 hot tables и thread-pool churn.
  • Reverse-order overlapping pending updates в одном random buffer.
  • Process/power loss посреди backup restoration после удаления per-record Flush.
  • Remote reparse-point/junction escape и TOCTOU внутри root.
  • Remote open/close storm под continuous I/O и latency global write lock.
  • Raw protocol cross-version pair matrix и explicit semantics short-read/cap.
Execution note. Финальный полный Release-прогон прошёл целиком. Непосредственно перед ним один прогон остановился на 30-секундном timeout ParallelMultiTableCommitsRemainDurable после первого PASS; повтор без изменений прошёл. Это не Storage-specific functional failure, но timing-flake стоит учитывать в CI.

12. Заключение

Refactoring в целом движется в правильную сторону: .NET 8 получил настоящее параллельное чтение и modern positioned I/O, а allocation-heavy recovery/backup/remote paths стали bounded. Формат БД, pointer encoding, backup records и remote v1 layout сохранены и подтверждены compatibility probes.

Главный глобальный урок — проверять не папки, а граф компиляции target-ов. Именно отдельная Portable ветка сохранила незакрытый remote path gap и ранее повторно внесла legacy backup regression; selector теперь синхронизирован и проверен. Второй урок — Allocated/op и latency не заменяют working-set контракт: Clear(false) дал сильный выигрыш, но изменил память с «почти 1 KiB после flush» на «до 1.08 MiB на каждую hot table».

Рекомендация: не откатывать современные .NET 8 решения. Random64ByteRead gate и Portable backup P0 закрыты. Остаётся решить MEMORY no-op contract, ввести bounded shrink policy и определить Portable remote containment; после этого архитектуру Storage можно считать совместимой с эталоном при существенно лучшем high-load профиле.
